# PAD 23.6.1 多轉轉、連續取色的原生依據

2026-11-07。這次以現有 PAD 23.6.1 IDA 資料庫作只讀核對，再用官方公告及日文攻略交叉比對遊戲規則。**原生程式支援多個轉轉，也沒有把連續取色限制成單次、單色。** 求路器應按當前隊伍及盤面目標安排所需色序；CPU 搜尋額度與遊戲容許的操作是兩件事。

本次輸入 SHA256 為 `3ac8c5647e67694b5a3e68cf7049d3860f82f029a7e67f96477e9e2a3f490fd6`。以下皆為這份 23.6.1 二進位的未加載入位移位址；不能套用到其他版本。先前 [單次／雙次取色研究](solver-fishing-2026-11-06.md) 的方向得到重新核對，但本次另記函式位元組雜湊與指令位置，不以舊版測試取代新證據。

## 多個轉轉可以取色，但要逐格追蹤

`0x1005AB5F4` 在更新條件成立時遞減共享倒數 `impl+0xB4854`；倒數到零便從 `impl+0xB4844` 重設週期，按 `impl+0xB4864` 的逐列遮罩走訪所有有效轉轉格。程式不是只處理第一格。

每格只有在目前珠子的 `orb+0x12 == 0` 且未鎖時才變色，鎖定依據是 `orb+0x4` 的 `0x800` 位元。拿起珠子會設為狀態 4；交換時被推走的珠子設為狀態 3，兩顆珠開始移動插值。因此即使所有轉轉共用倒數，有一顆被拿住或正在移動，便會跳過其他格已發生的 tick。**原始盤面各轉轉間的色相差，經過路徑後不一定保持。**

| 23.6.1 證據 | 已確認行為 | 對求路器的要求 |
|---|---|---|
| `0x1005ABA0C`／`0x1005ABA1C` | 分別檢查每顆珠的動作狀態及鎖定 | 不可把共享倒數等同於所有格都曾變色 |
| `0x10060F460` | 初次持珠設狀態 4 | 在轉轉上拿住等待不會讓持珠繼續變色 |
| `0x100608B30` | 被推珠設狀態 3 | 每次交換後要等對應珠恢復穩定 |
| `0x100608B98`／`0x100608BA4` | 交換珠子指標，而非只交換顏色 | 強化、鎖、其他附帶資料跟隨珠子身分重播 |
| `0x1005ABE0C` | 插值 current 等於 target 且狀態非 4／5，才清為 0 | 不能把插值參數 0.125 直接視為已驗證的固定八幀等待 |

轉色處理在這個 updater 的移動處理之前。某顆珠在同次更新稍後才恢復狀態 0，可能已跳過這次 tick。因此連續取色至少應在每次交換後，讀回所有轉轉的實際顏色與珠子動作狀態，更新後續推算；只累加共享倒數不足以保證重播正確。

正常取色的順序是持珠停在目標格旁，讓目標格的非持珠到達所需顏色，再進入該格，把那顆珠換到前一格。後續再次進出同格或改用其他轉轉，仍要維持同一條連續持珠路徑，不能把獨立的顏色交換當作已可執行手勢。

### 指定色轉轉必須讀實際色表

這次亦確認色表是這個盤面的共用欄位，並非每格各存一份：`0x1005AB9B4` 固定使用 `impl+0xB4FD0`，逐格在 `0x1005ABA28`／`0x1005ABA4C` 解碼同一個 mask。原始 mask 為 0 時，`0x1005ABA30` 轉到普通火→水→木→光→暗→心→火分支；非零則在 `0x1005ABA38–0x1005ABA60` 按色碼由小到大、循環尋找下一個有設定位元的色，直接略過不在表內的色。這些位元搜尋迴圈在同一次轉色更新內完成，不是逐色額外等待一幀。

對目前支援的基本色子集（色碼 0–5、至少兩色，珠色已在表內），原生下一色與 `PHOrbSpinnerType` 的「下一個允許色」結果一致。例如木／心表為 `36`，週期就是木↔心，不會途經光。`ReadSpinner` 只把原始 0 正規化成 `63`，非零表保留原值。因此目標要先與實際色表相交：需要光但表內沒有光，不能排等待光的路徑；色表中途改變亦須撤銷舊方案。共用色表不代表所有格當下顏色相同。指令證據另見 JSON 的 `N8`。

## 放手色與消除判定色要分開

`0x1005B5180` 的正常 phase 2 分支在 `0x1005B59C0` 呼叫輸入處理，之後經共同尾段於 `0x1005B5538` 呼叫轉轉／珠子更新器。這是控制流程次序；函式內較小的指令位址不代表較早執行。

放手分支會呼叫 `0x100602FA0` 做旗標及持珠狀態清理；`0x100603DF4` 仍會檢查移動。狀態 1–3 阻擋匹配；狀態 4 若 `orb+0x24` 與 `orb+0x28` 的插值數值不等也阻擋匹配，另有特殊狀態檢查。到 `0x100604044` 才呼叫原生匹配 `0x1005FC954`。

所以畫面上看到想要的顏色、送出最後一步、放手、原生匹配，是不同事件。若最後布局在全部允許的判定相位都成立，可以避免依賴單一放手幀；但那些相位必須從路徑後真實的各格顏色推導，不能沿用已因持珠跳 tick 而失效的起始相位。只靠某個顏色的條件解，仍需要手機量測放手至匹配的窗口。

## 特殊珠能轉色，不等於已可直接放寬模型

普通色表的原生分支在 `0x1005ABA68–0x1005ABA74`：目前色碼 0–4 加一，其他正常有效色碼回火 0。因此心、妨礙／毒等珠在符合狀態及鎖定條件時，可能下一次轉色成火；並非天生不能透過轉轉換掉。

自訂色表走 `impl+0xB4FD0` 的另一路徑。其結果為色碼 6–9 時，`0x1005ABA98` 清除 `orb+0x8`，後續並清除旗標 `0x28000`。模型若只改色碼、保留不該保留的附帶資料，就會偏離原生結果。這次沒有據此放寬特殊珠支援；完整轉換規則、毒與回復結算仍要另外核對。

## 接入與裝置驗證要核對的事項

1. 每次取色前確認目標珠已非持珠、已穩定、未鎖，實際色符合此次要求；交換後核對珠子身分、盤面與所有轉轉相位。
2. 累計取色等待、移動、穩定及最後輸入餘量；剩餘時間不足便停止增加取色，不能借用尚未驗證的八幀假設。
3. 多轉轉終盤由實際相位基準評估全部允許色序；條件放手解與全相位解分開記錄。
4. 手機量測讀取／輸入／轉色相對次序、交換恢復穩定、放手至匹配及中止行為。多次取色成功率、耗時與新候選搜尋仍待明確編譯測試後執行。

這些是接入要求及待驗證項目，不是已通過案例。盤面與既有路徑問題另見 [本次路線檢視](solver-route-review-2026-11-07.md)。

## 再後續：珠量通過後最多多取兩次

目前來源已處理上述位置限制的一部分。Session 在一般／回復連撈中啟用額外取色：從已選中的合格珠量方案，各自延伸最多兩次真實交換，總數仍不超過六次，並保留原有完整目標。共用入口預設不延伸，既有呼叫不用改變；這項來源尚未編譯進已交付版本。

原補珠候選先枚舉與選取，順序及已選名額保留。延伸只用十二案中的空位，最多四案；新狀態最多 512 個，與原規劃合計不超過 8,192，且使用同一規劃截止時間。先按目標色與附近犧牲珠排序，再交替保留多一／兩次的候選；只有一個空位時優先多兩次。已佔滿名額或狀態／時間不足會略過，不拿額外方案替換原有五／六次缺珠方案。

若至少一個保留的額外方案，以每次交換最少兩步計算後能通過步數及剩餘操作時間預留檢查，剩餘路徑搜尋時間才劃出約三分之一供額外方案使用，原方案先搜尋約三分之二；原方案提早結束的餘時也可給額外方案。沒有保留額外方案，或全部未通過最低操作時間預檢，原方案沿用完整搜尋時間。這會重新分配搜尋時間，加上額外珠量枚舉成本，不能宣稱原候選的搜尋覆蓋不變或整體效能必然改善。候選格仍共用一次回退時間，沒有按每色或每格另發完整額度。

新增書面小圖案例已經有四顆心，但心全在封條格，普通可移動區域只有木珠。可移動區域的顏色不變量與單次取色可落點，分別排除零／一次取色滿足全相位心四連；`7→14→8→14→15` 則是兩次木換心的四步手算路線，最後心四連在 `7／8／9／10`，木／心兩種轉轉終色皆成立。獨立交換與完整消除群組核對也已寫入案例，**尚未執行案例或新求路器，不是實測成功紀錄**。
