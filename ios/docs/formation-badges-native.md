# 編隊徽章：保存範圍與原生來源

2026-11-07。這批將徽章選擇納入每份編隊的保存／分享資料。**保存編隊徽章不會自動更換遊戲目前使用的徽章；實際徽章仍須在遊戲中選用。**「徽章解鎖」是另一項全域功能，不能用它的開關或 ready 狀態表示某份編隊的徽章已套用。

## 三個不同狀態

| 狀態 | 意義 | 不能據此宣稱 |
|---|---|---|
| 編隊保存的徽章 | 該份隊伍配方希望使用的徽章，可隨隊伍保存和分享 | 目前遊戲已選用／戰鬥效果已啟用 |
| 全域徽章解鎖 | 既有 `PHBadges` 對有效所有權位元的處理狀態 | 已替某份編隊選擇徽章 |
| 遊戲實際徽章 | 原生 getter 按遊戲模式、關卡和遊戲已存隊伍計算的有效結果 | 一定等於編隊分享資料中的數字 |

保存欄位缺省時表示未指定、沿用遊戲選擇；明確 `0` 是分享資料中的「無徽章」，兩者不能合併。這是編隊／PADDashFormation 交換格式的選擇值，包含其合成代碼，**不是可直接寫入原生存檔的 ID**。具體 UI 與互通規則須以本批編輯器實作為準。

`PHFormationReadBadge` 只解析 optional 整數欄位，拒絕布林、null、分數、非有限值及範圍外的值；無效資料不修改輸出，也使整份隊伍驗證失敗。它不修改六名隊員的 loadout、不讀寫遊戲徽章。範圍內的未知分享值可以保留，但不表示遊戲存在或帳號可使用該徽章。

## 23.6.1 原生核對

本次只讀開啟 `build/ios-address-23.6.1/23.6.1/pad.i64`，核對 IDA input 路徑與 SHA256，以及本機輸入檔 21,574,784 bytes。SHA256：`3ac8c5647e67694b5a3e68cf7049d3860f82f029a7e67f96477e9e2a3f490fd6`。以下位址全部為此輸入的未加載入位移位址。

10 個函式的完整範圍及 bytes SHA256、主張和呼叫點見 [研究 JSON](../research/formation-badges-20261107.json)。`battle-23.6.1.json` 的 `PHBattleCurrentBadgeRVA` 與 `PHBattleBadgeBoostRVA` 各 64-byte guard 已與 IDA bytes／hash 核對。沒有重驗全部 target guards、IPA Info.plist、Mach-O UUID 或裝置載入映像。

### 有效徽章由原生規則決定

`0x1005A069C` 每次呼叫會重新判斷來源：

1. 原生 mode 11 或 5 返回 `0`。
2. 從 game `+0x70` 取得 impl，再讀 impl `+0xB0F20` 的關卡指標；空指標返回 `0`。
3. `0x100240480` 查詢關卡欄位 119，成功且值介於 `0` 與 save `+0x24E8` 的 signed16 徽章數量之間時，直接採用關卡指定值。
4. 沒有有效指定值時，`0x1002409B8` 的關卡欄位 19–24 條件成立便返回 `0`。
5. 其餘情況呼叫 `0x100006A0C`，讀取目前遊戲已存隊伍的徽章。
6. mode 7 配合已觀察到的狀態非零時，另讀當地隊伍資料來源；值 `10` 會被轉為 `0`。

這次保留 mode 數字，沒有重新確認每個多人模式名稱。以上結果證明一般 fallback 取自遊戲已存隊伍，並受原生關卡／模式規則覆寫；**沒有在本次範圍內建立可供編隊功能呼叫的獨立戰鬥徽章 setter**。

`0x100006A0C` 讀 save `+0x52F392` 的 signed16 選隊索引；超出 save `+0x52F38C` 的上限或 32 時歸零。隊伍記錄由 save `+0x52F39C` 起，每筆 96 bytes，徽章在 byte 95。`0x100445DA4` 的解碼為 `raw XOR uint8(15 × bankIndex + 0x61)`。這個位址發現不是任意改寫存檔的介面。

### 徽章在後續計算仍會被讀取

`currentBadge` 有 17 個已列出的直接呼叫點。本次重點核對：

| 呼叫點 | 消費方式 |
|---|---|
| `0x1005B7480` | 戰鬥建構中，取得徽章後交給原生 SB helper |
| `0x100604A74`、`0x100604A8C` | 操作時間計算的徽章項，以及額外有效 kind 條件 |
| `0x10060A658` | 後續耐性／效果分支取得有效徽章 |

因此，只在換隊重建或初始 SB／HP 計算期間暫時換值，計算後立即恢復，不能保證稍後的操作時間、耐性等效果一致。`PHBattleEntry.inc` 的 `InitialTeamBoost` 繼續呼叫原生 `currentBadge(game)`／`badgeBoost`，不應偷偷換成編隊保存的數字。本次並未完成所有 HP、攻擊、武裝及耐性消費者的完整審核。

### 選擇 ID、有效 kind 與顯示名稱

`0x10056CCCC` 從 save `+0xA0` 的 180-byte 徽章表讀取參數；每筆 `+176` 的前置徽章若已擁有，且呼叫沒有要求 raw 資料，會改讀前置徽章。有效 kind 不一定等於選擇 ID。

`0x10056D598` 以有效 field 0 判斷 SB：kind 23 取 `field2 / 100 % 100`，kind 7 取 `field2`，其他為零。因此不能只按一份歷史 ID 清單推斷加速或其他效果。

`0x10056CE04` 的名稱來源是 save `+0x98` 指向的名稱表，也可替換成已擁有的前置徽章；ID 1 另有動態格式化。本批未呼叫或接入這個函式，不把靜態分享名稱宣稱為即時原生目錄。

`0x10000680C` 校驗遊戲已存隊伍時，遇到無效或未擁有的徽章會寫回編碼後的 ID 1。這是原生修復行為，不能混同於編輯器的缺省選擇或明確 `0`。

## 本批邊界與待驗證

既有 `PHBadges` 只提供解鎖狀態；`PHDeckPersistence` 只在帳號、隊伍 identity、資料就緒及較新選擇等條件通過時，回蓋先前已確認的遊戲本地選擇。本批沒有把這個回蓋器變成配方 setter，也沒有新增存檔寫入、戰鬥徽章攔截、暫時租用／恢復或多人變更。

本次只做原生來源及源碼 review，沒有修補、改名或主動保存 IDA 資料庫，沒有編譯、執行測試套件、派發 CI、打包或操作裝置。新增資料模型與分享案例仍待明確「編譯測試」後執行；iPhone 上也要核對保存／重開、切換／複製隊伍和分享往返，並確認畫面沒有把「保存徽章」顯示成「已在遊戲套用」。
