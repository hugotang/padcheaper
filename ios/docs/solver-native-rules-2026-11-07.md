## 先找直線，再按實際消除群判定

原生 `0x1005FC954` 的正常消珠流程為：

1. `0x1005F4048` 初始化工作色與暫時標記；盤寬／高來自 game `+0x58/+0x59`。
2. 逐格處理時，先按有效消不掉狀態及色表排除顏色，再由 `0x1005F780C` 預掃上下左右連通的同色珠。
3. `0x1005F8E28` 對預掃範圍分別尋找橫／直連線。長度須達 game `+0x5C`，也就是 `minErase`；達標格才設 run 標記。
4. `0x1005F7B38` 沿相鄰且已標記的格計數。主呼叫點在 `0x1005FD89C–0x1005FD8B8` 再以 impl `+0xB6264/+0xB626C` 兩個 signed 16-bit 值的較大者檢查群大小，即 `minMatch`。
5. `0x1005F7CD8` 真正標記消除、回傳消除數，再建立本群的形狀旗標。這個回傳值才供四珠、五珠、攻擊等後續分支使用。

`minErase` 是「連線要多長」，`minMatch` 是「消除連通群要多大」，不能混成一個要求。例如 `minErase=3、minMatch=5` 的五珠 L 可成立；`minErase=4` 時孤立五珠 L／T／十字與孤立 3×3 都沒有合格連線，不能先按外形直接判成功。

原生的預掃同色連通群不等於最終消除群。旁邊同色珠若沒有進入合格連線，不會僅因相鄰便使 L／T 失效；若它延長連線並加入同群，則五珠形狀失效。相鄰是上下左右，斜向相鄰不合併 Combo。允許斜走的移動選項不會改變消珠鄰接規則。

有一項實作細節不應抹平：`0x1005F7B38` 會把起點設為 visited，即使起點本身沒有 run 標記；後續只遞迴進入 `flags & 3 == 2` 的鄰格，分類器又再次按橫／直連線實際移除。因此本頁以標準穩定盤的最終消除群對照，不把暫時計數、特殊工作旗標或非標準動畫狀態宣稱為完全等價的純集合模型。

## 各形狀的確切條件

形狀旗標位於 impl `+0x92E12` 起，分類器每群重設。以下條件先決是該群已通過消珠規則。

| 規則 | 23.6.1 原生證據 | 共享求路器對照 |
|---|---|---|
| 橫／直 run | `0x1005F8F18`、`0x1005F909C` 讀取 `minErase`；`0x1005F8F50` 等設 run 標記 | `MarkedRuns` 分色標記橫／直線 |
| 消除群大小 | `0x1005F7B88–0x1005F7B94` 只累計 run 格；`0x1005FD89C–0x1005FD8B8` 檢查 `minMatch`；`0x1005FD8D8` 呼叫真正分類器 | `EvaluateStatic` 在已標記的同色連通群上檢查門檻 |
| T | `0x1005F8430` 要求實際數量 5；四方向幾何分支；`0x1005F854C` 設 `+0x92E17` | `ShapeMatches` 要求整群等於其中一個五格 T |
| 十字 | `0x1005F8910` 要求 5；中心橫三的上下臂；`0x1005F89C4` 設 `+0x92E14` | 整群必須等於五格十字 |
| 3×3 | `0x1005F89D0` 要求 9；三行三列逐格核對同色及有效狀態；`+0x92E15` | 整群必須等於九格正方形 |
| L | `0x1005F8B04` 要求 5；四方向端點分支；`0x1005F8C84` 設 `+0x92E16` | 整群必須等於其中一個五格 L |
| 四珠 | 呼叫者 `0x1006008EC` 直接要求消除數量 4；心色分支另見 `0x1005FEC38–0x1005FEC48` | 支援的 `minErase≥3` 下，合格四格連通消除群只能是橫四或直四；因此直四模板與這個數量條件等價。不能把三連旁的一顆未消珠計入四珠 |
| 滿橫行 | `0x1005F7FD0–0x1005F7FF0` 要求本行從 x=0 開始、消除數達盤寬，設 `+0x92E12`；不要求整群只有一行 | 普通 Row 及首消加成 Row 都允許群內有已消除支枝 |
| 原生滿柱旗標 | `0x1005F8CAC–0x1005F8CC4` 要求群的 minX==maxX 且消除數≥盤高，設 `+0x92E13` | `bonusFirstWave` 的 Column 要求整群恰等於盤高，符合單柱；**普通 Column 是既有產品語義：群內含滿柱即可，允許支枝** |

L／T 的端點同時核對 state 5、工作色 -1 及相同色。十字與 3×3 的額外格核對非 state 6、未設特殊排除標記及相同色，並配合總數 5／9。沒有查到「整圈所有相鄰珠必須異色」的原生規定。舊資料提到的形狀四周隔色限制，不能再作為當前 solver 的必需條件。

普通 Column 與原生柱形覺醒的差異已由 [EnemyComboSolverTests](../tests/orb_enemy_combo_solver_tests.inc) 明確保留。不能為了對齊覺醒旗標，順便收緊使用者已保存的一般 Column 目標。

## 連鎖、首消及轉轉的邊界

`0x100603DF4` 先等待移動／消除狀態，於 `0x100604044` 呼叫匹配。原生 `0x100603360` 會把未消除珠往下整理，為消除位置準備新珠；色彩準備呼叫在 `0x10060349C`，另有固定來源分支。`0x100603884` 呼叫補珠抑制條件，成立便把新珠標成 state 6；未成立則繼續掉落、穩定及再次匹配。這次只追到該控制邏輯，未完整還原新珠分布、所有無天降來源、敵人效果及每一個覺醒的跨波次結算。

原生形狀分類器本身沒有「只准首消」參數，且正常匹配主鏈會再次呼叫它。求路器的 Exact、L／T／十字／直四／3×3／Row／Column 只接受首消，普通 Combo／Colors／Match 可接受既有珠落下形成的確定連鎖；`comboFirstWave`、`bonusFirstWave`、活動模式會進一步限制計分。這是可執行目標的保守政策，不是所有原生覺醒只認首消的證據。

求路器不生成隨機天降珠，因此後續連鎖結果是「只讓已知珠掉落」的模型。補進的新珠可能延長、合併原本預測的群；不能把普通總 Combo 或連鎖形狀當作無條件的原生保證。需要保證首消的敵人對策及加成證據必須繼續使用首消欄位。

轉轉方面沿用已核對同一二進位的 [原生取色研究](solver-native-fishing-2026-11-07.md) 及 [證據 JSON](../research/orb-multifishing-native-20261107.json)：共享時鐘逐格更新；只有未鎖且 state 0 的珠變色；持珠及移動珠可各自跳過 tick；指定色表按允許色循環。故可多格、多次、多色取色，但要按隊伍目標、實際色表與剩餘操作時間規劃，逐次讀回顏色及動作狀態。這個結論並不提供已在 iPhone 量測的安全等待幀數。
