# 技能拒絕、待命選擇與轉珠時間

2026-10-29，使用者提供兩隊的 0.5.3 裝置資料。0.5.4 原始碼包含下列修正與診斷；建置進度以 [開發紀錄](development.md) 為準。完整裝置 log 留在 repo 外。

## 裝置證據與未確認部分

夜一 #14055 位於位置 2，規則順序為 1、5、6、4、3、2，對應規則 6。使用者已確認該規則顯示「冷卻尚未完成或遊戲判定技能無效」。表示當次確實進入原生 can-use 並被拒絕，不能用規則 2 的事件或殘留選擇 gate 解釋。停止自動後手動點擊可立即施放，但舊診斷沒有保存拒絕當時的實際技能與冷卻。

新隊伍為 #14035、#14043、#14175、#14190、#14200、#14184，六條規則均按位置順序、每回合、獨立施放。位置 3 是ユークス＆ミヤ，武裝 #11598。使用者確認手動施放的是進化後的解鎖／光暗心改盤技能，而非首次加速技能。

新截圖的規則 3 在位置 4、5、6 技能完成後均重新嘗試，仍被原生拒絕，排除了「拒絕快取沒有清除」。位置 3 進化後本體技能 ID 65778、資料表 CD 5；武裝技能 ID 47509、CD 20。實際關卡冷卻須以原生結果核對。

截圖最後是轉珠 39/45、本次連續 turn 1 / moves 0 / skills 5；複製 log 時已是 phase 0、wave 9、累積充能 5。這些即時數值晚於技能判斷，不能證明拒絕當時已有 5 充能。中斷轉珠後的消除可能讓充能由 4 變 5，需新版保留的當次資料確認。此處沒有把手動成功當成需要繞過原生判定的依據。

## 轉珠時間缺陷

舊 executor 從 afterFrame 確認交換時重新計算 65 ms 間隔，但求路只按兩個 30-fps frame、約 66.7 ms 估算。實際渲染與讀取占用幾毫秒後，下一次滿足間隔可能變成第三幀，約 100 ms；45 步可能超過原有 4 秒上限。39/45 與此路徑一致，但舊版共用停止文字不足以單獨證實當次是逾時。

0.5.4 從提交目標的 frame 計時，交換仍須完整確認才能前進；延遲確認不能跳格。保留 65 ms 間隔、4 秒總上限與原生操作時間。逾時、手動操作、盤面限制、遊戲結束拖珠及開關變更分別顯示原因；記錄本次執行耗時。另將新求路的確認步數／起點狀態一起歸零，避免上一條路徑進度混入失敗候選。

## 待命選擇修正與拒絕診斷

殘留選擇是獨立確認的程式缺陷，尚未證實是使用者原生拒絕的原因。舊版一律略過非預設選擇過於嚴格；直接刪除 gate 而不清除舊值，也可能導致檢查當前技能卻消費舊 ID。

0.5.4 只在待命、單人、無手動輸入、原生 can-use 成功且快照一致時，清除目標的殘留選擇；讀回和再次核對後才啟動。只寫預設 sentinel，不寫技能 ID、充能或使用次數。拒絕時不清除，進行中的對話框仍阻止操作。新增 reset 指紋涵蓋清除指令，但不呼叫函式中段。

原生拒絕後才取得四個已校驗 getter 的技能／CD 明細，接著重新確認狀態。訊息區分「冷卻尚未完成」與「冷卻已足，遊戲仍判定技能不可用」；未取得資料則明確標示未知。技能 ID 使用 32-bit，涵蓋 65778 等超過 65535 的值。診斷不改變 can-use 結果，不強制施放本體或武裝。

ruleDecisionDetails 保存規則、位置、角色、原因、當時充能、選擇、階段、等級及使用次數。面板標明規則和位置，複製 log 逐行列出所有判斷；停止後讀取及通用設定回載不會抹掉。原生拒絕的完整明細保留在當次原因文字中。

## 驗證與真機後續

回歸覆蓋待命殘留選擇、原生效果消費當前技能、充能不變、拒絕不寫入、選擇與階段競態、寫入／讀回失敗、多人切換、全部非待命狀態、指紋失效、規則／位置映射、停止後保留資料、五個技能成功但進化技能差一回合、下一回合重新施放，以及 30 fps 帶 12 ms 渲染耗時的長路徑與真正逾時。

真機核對位置 3 拒絕當時的充能／CD／階段、改盤後技能順序、完整路徑與下一回合接續；另核對夜一的本體／武裝選擇及同回合不重複。既有交付目錄及 ZIP 不變；device_verified 維持 false，測試替身不能證明裝置技能結算已修復。
