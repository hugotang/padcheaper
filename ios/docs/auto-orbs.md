# iOS 自動轉珠 — 0.5.4

本頁含 0.5.3 的轉轉、雲、封條、暗闇、特殊珠及複合形狀搜尋；這些新增能力不存在於既有 0.5.2 dylib。支援與限制詳見 [盤面效果](orb-effects.md)，測試／編譯狀態以 [開發記錄](development.md) 為準。

本版擴充單人「讀盤並求路 → 路徑預覽 → 執行一次／停止」，加入 7×6／5×4、求路品質、指定形狀與部分隊長盤面條件解析，另加入明確按下開始的連續轉珠與可設定技能規則。編譯、自動測試與真機結果分開記錄於 [驗證記錄](development.md)。連續模式只處理目前關卡，不自動選關或接續結算；詳見 [連續轉珠與技能規則](orb-automation.md)。

使用者已於 2026-10-28 回報 `0.5.0-orbs` 測試通過，作為普通單人 6×5 的真機基準。新版 CI 53 已通過離線求解、原生記憶體／輸入 fixture、編譯及 iOS 介面；新增內容仍待真機驗收，見 [驗證記錄](development.md) 與 [真機順序](device-testing.md)。

## 使用

PC 浮動入口旁可直接按「轉一次」或「開始自動」。「轉一次」沿用已儲存的目標與品質，讀盤求路成功後自動執行一條路徑，不施放連續模式技能，也不接下一回合；「開始自動」沿用既有策略與技能規則。工作期間按鈕變為「停止」，短訊息直接顯示狀態；拖動 PC 可把整組按鈕移到另一側。隊伍正在套用或還原時先等待完成。

1. 新版完成建置後，進入普通單人 6×5、7×6 或 5×4 關卡，等待操作階段並放開手指。
2. PC 面板 →「自動轉珠 · 連續／技能規則」→選擇「快速／均衡／深入」及「高 Combo／指定形狀／隊長盤面」→「讀盤並求路」。設定寫入成功才生效；舊 config 預設均衡、高 Combo，變更後需重新讀盤。
3. 核對珠色及效果標記。後續效果批次增加邪魔／毒／猛毒／爆彈，以及雲、封條、暗闇、轉轉、鎖／弱化等標記。盤面由上到下、由左到右顯示；滑桿逐步重播，文字標明起點與目前格子。目標或毒／爆彈條件未通過時只供預覽，不可執行。
4. 開啟 PC 功能總開關後可按「執行一次」。頁面收起，等待 0.35 秒後開始。浮動按鈕變成「停止轉珠」。
5. 「執行一次」完成後會放開，不會接續下一回合。若選「開始連續轉珠」，每回合自動處理已保存的技能規則並重讀求路，玩家觸碰遊戲或按停止便中斷；沒有技能規則時只會連續轉珠。

預覽計算目前珠子的消除及既有珠落下的連鎖，後續批次套用原生最少消珠及不可消限制，不計隨機天降、隊長／Combo 珠加算或隊伍傷害。可要求 L／十字／T／3×3／整橫排／整直行／四連，以及連消、多色、最低 Combo。形狀以首批消除為準，最多 6 項條件；詳細規則與隊長解析界線見 [形狀與隊長盤面](orb-goals.md)。「預計 Combo」不是保證結果或最優解。

已交付 0.5.2 接受基本六色、0 到 1 的強化及鎖珠，其他效果仍受舊 gate 限制。後續原始碼接受十種已知珠型、−1 到 1 強化值與已核對效果，套用不可消、最少消除及固定起點；路線避開封條／刺珠／轉轉，轉轉全部共用相位皆須達標，毒／猛毒不能確定性消除，爆彈須首批全消。未知或不一致資料仍拒絕。可先按規則使用指定技能，完成後重讀；詳見 [效果適配](orb-effects.md) 及 [技能循環](orb-strategies.md)。多人偵測會鎖定本場，只有離開戰鬥才解除；舊設定的 allowAllMulti 不能覆蓋限制。首次讀盤後維持低頻場景監測，短暫讀取失敗不會阻止觀察離場，也不會自行解除多人限制。

盤面大小由原生記憶體讀取，不提供手動強制尺寸。每一格都核對物件池、珠子指標及等距格心；預覽使用實際行列數。回合內尺寸變動會作廢舊路徑，不對新盤面送出舊輸入。原生頁面的返回與讀盤／執行按鈕固定顯示，盤面和說明可捲動。

## 原生邊界

唯一版本是 iOS PAD 23.6.0／106878，UUID `DD332AD4-4C92-3AAF-85D0-3892556A3A0E`，原始 executable SHA256 `611c93f5472fceddfa27254b718c6eff1decdc6814cc927e2faa4c7c250a65ec`。`orbs-23.6.0.json` 記錄獨立的程式指紋；現有版本／UUID gate 仍生效。

| 位置 | 靜態證據／用途 |
|---|---|
| GameMain +0x70 | 指向目前 battle impl，並與 active impl 及 scene table 比對 |
| GameMain +88/+89；+92/+93 | 行列數、最少消除數及自由移動模式 |
| impl +624832 | 256 個 172-byte block 的物件池 |
| impl +668864 | 16×16 格子指標表；每次重新解析，原生 row 0 位於畫面底部 |
| block +0/+1/+4/+8/+12 | byte 珠型、暗闇回合、完整 flags、強化 float 原始位元、刺珠傷害百分比 |
| block +18/+24/+26/+28/+30 | 動畫狀態、顯示座標、native nearest 使用的格心；靜止為 state 0 |
| impl +624824／+601668 | 拖珠指標與原生交換次數，用於逐步確認 |
| impl +603024／global +0x1b4ef58 | 原生剩餘操作 frame 與 frame rate |
| impl +738932/+738948 | 保護值 fixed-start X/Y；新批次轉為只能從該格開始的限制 |
| impl +739268／+739272 | 原生 match 函式先檢查不可消 effect duration，再按珠色檢查 mask |
| global +0x2ac6fd8 | 2672-byte 觸控 manager，5 筆 raw +5 筆 frame，每筆 264 bytes |

讀盤是純記憶體快照：檢查範圍、池對齊、重複指標、同一 scene/account/entry/wave、受保護值一致性，以及規則、格心與動畫。`_getNearestBlock` 會改 fixed-start latch，因此不拿它當 getter。需要兩份相隔至少 0.15 秒的一致快照才求解；新批次僅容許已建模轉轉的共用色序推進及原生普通暗闇／起點暗化清除，其餘資料仍須一致。

拖珠沒有改寫珠型、交換表、傷害或操作時間，也沒有建立任意 UITouch、patch 指令或依賴 JIT。只有原始 drawFrame 呼叫期間，把 global input pointer 暫時指向 session 持有的私有 manager。遊戲自己的 raw→frame 更新及玩家輸入函式消費 began/held/ended，原生函式負責交換、扣時間、釋放與消除。`@finally` 立即恢復原始 manager，真實 UIKit 事件始終保存在原始 manager。

這個 manager 使用範圍依據是已檢視的同步原生 frame 與 input lifecycle，並已有 `0.5.0` 普通 6×5 的使用者真機通過回報。新增尺寸仍需新版驗收。原生座標轉換函式的基底經求逆與 round-trip 檢查；不假設螢幕像素等於盤面座標。

每一格交換都核對所有 cell tokens、珠型、旗標、效果資料及原生交換次數，按上述有限容差確認後才能前進。每步至少 65 ms；三種品質的最大步數見下表，求解還會按原生可用時間、完整 frame 間隔及 4 秒執行上限縮短路徑。深入模式不加快拖珠。未接受起點／交換 0.2 秒後中止；恢復指標失敗保留 allocation 與 lease，設 release 並重試，且禁止再次開始。

0.5.4 從提交目標的 frame 計算間隔，修正渲染／讀取耗時累積導致 30 fps 長路徑超時；仍須交換確認才可送下一格，不跳過未確認步驟。停止原因區分執行逾時、手動操作與盤面限制，並記錄本次耗時。詳見 [技能與計時修正](orb-skill-selection.md)。

0.5.2 每條路徑只送一次 began，之後保持 held 並保留私有 input bank，支援下一幀才選珠的 iPhone layout。起點拒絕或手動停止後，清理不覆蓋原始原因；新增 `Orb start: sent / accepted` 診斷。新版建置與真機結果分開記錄於 [驗證記錄](development.md)。

手動介入時只送自己的 release，真實觸控留待遊戲下一幀處理。場景、樓層、帳號、多人或 input manager 改變時，丟棄意圖，不把舊清理寫進新場景。離開前景會取消工作，回前景不恢復路徑。

## 核心與取消

參考 [pazusoba/core](https://github.com/pazusoba/core) 及 `E:\pad\ultimate` 的新分支。後者的 Python auto 流程確實存在，也已補完 shape 分支；本版沒有把它當成缺 Python 或 shape 空白的 upstream 版本。

iOS 核心是受限的 C++ beam search adaptation；保留 [MIT 授權](../third_party/pazusoba/LICENSE) 及 [來源說明](../third_party/pazusoba/NOTICE.md)。不編譯 Android CLI、OpenMP、x86 BMI、長存 cache 或直接 exit 的路徑。只用一個 serial background worker，預設均衡；API 上限 512／1000 ms／48 步。

| 品質 | 最多步數 | beam | 搜尋時間預算 |
|---|---:|---:|---:|
| 快速 | 24 | 128 | 120 ms |
| 均衡 | 32 | 256 | 350 ms |
| 深入 | 48 | 512 | 800 ms |

較高品質搜尋更多候選，並不保證每個盤面都得到較高 Combo 或完整目標。候選、路徑與本層 visited 的大小皆有界限。工作持有 immutable board、目標與取消旗標，換預覽／停止／切換品質或目標就增加 generation；舊 completion 不得發布新結果。品質保存於 `orbs.quality`，只接受 `fast`／`balanced`／`thorough`。目標模式與手動條件保存在 `orbs.mode`／`orbs.goals`，變更品質不會刪除它們。執行中不能用介面切換設定；外部設定變更於這次執行結束後套用。

0.5.3 的 [複合形狀搜尋修正](orb-shape-search.md) 增加補珠／拆組及布局衝突估計，每層約四分之一名額保留不同缺項與布局並穿插展開。四連改依實際首批消除群組，未消同色鄰珠不再誤拒絕；品質預算維持上表。桌面對照的達標數與耗時見該頁，真機表現仍須核對。預覽與停止原因另列缺少條件及求路時間，與預計拖珠秒數分開。

求解後獨立重播路徑再發布；執行按鈕附帶預覽 generation。45 秒後或真實盤面有變就作廢，避免執行未看過的新路徑。

## 自動測試範圍

以下既有套件新增效果及形狀案例，各套件本批執行結果見開發紀錄；不能以 0.5.2 的成功紀錄作為本批驗證。

- `orb_solver_tests.cpp`：24 個固定種子、三種尺寸與三種品質；獨立 run/union/gravity oracle；不可變快照、非法跳格、舊 token、取消、時間與 beam/depth 上限。
- `orb_shape_solver_tests.inc`：新增四連未消鄰珠、合併群組、首批／連鎖、轉轉與路線限制；光 T＋心四連及 IMG_0407 兩種條件 × 三種品質的待執行對照，含獨立首批四連 oracle。
- `orb_native_tests.mm`：三種尺寸的真實布局記憶體 fixture；首末格及額外列、尺寸改變、未知尺寸／旗標／不可消、多人 latch、private input、保留手動輸入、消除階段的放開確認、指標恢復失敗及 manager 取代。
- `orb_session_tests.mm`：preview 不注入、每步確認、三種尺寸的執行及最後一格放開、尺寸變更時取消、品質切換後失效、低 frame rate 的時間預算、只執行一次及既有中斷案例。
- 形狀／隊長案例：精確形狀及顏色、旋轉、第 42 格、同色分組、衝突與不足珠數、未達標執行拒絕、技能參數解析及未知條件阻擋、當前雙隊長 ID／pointer 核對、角色變化取消舊路徑。
- 設定／原生 GUI probe：品質保存及重啟、未確認儲存的 UI 回復、三種尺寸的顏色／比例／逐步預覽、固定操作列、generation 轉交與返回遊戲；保留既有編隊 GUI／儲存測試。新增連續與技能案例見 [規則驗證清單](orb-automation.md#自動測試範圍)。

新版真機先核對 7×6／5×4 讀盤，再執行一次並測停止、品質及目標切換，另核對形狀與隊長盤面條件。若被拒絕或路徑中止，PC 診斷會列出盤面尺寸、品質、目標模式與達成數、目前雙隊長、未支援條件、phase、步數、native move counter、剩餘 frame、搜尋上限、耗時與 input fault。先前通過回報不擴大到尚未驗證的新增內容。
