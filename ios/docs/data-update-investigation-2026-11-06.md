# 23.6.1 重開後反覆下載資料調查

**狀態：已依使用者指示擱置。** 使用者後續表示其他玩家也回報此 app 問題，要求回到 solver 優化。以下是當時的靜態調查，不代表已證明 tweak 為根因；文末對照步驟不再列為當前待辦，沒有實施診斷或修復。

2026-11-06。**已確認 Skin／BGM／徽章解鎖所改的記憶體會進入遊戲自己的 `data056.bin` 存檔；尚未確認這是每次重開下載約 25 MB 的原因。** 本輪只做來源與原版二進位分析、整理待驗證步驟，沒有修改產品來源、建置、執行測試、派發 CI、操作裝置或刪除遊戲資料。

## 使用者觀察與分析範圍

- 載入 tweak 時，資料更新完成，但下次開遊戲又要求下載約 25 MB。
- 在 LiveContainer 停用／移除整個 tweak，並刪除 Documents 內除 `048.bin` 外的其他 bin 後，重新更新可恢復正常。停用與清理是兩個同時改變的條件，不能據此推論單獨停用就能恢復。
- 恢復載入 tweak 後又會復發；發生時 Skin／BGM／徽章至少一項解鎖有開啟，尚未隔離是哪一項。
- 23.6.0 是首次製作及使用這個 tweak，23.6.1 是首次帶著 tweak 更新遊戲的版本；沒有更早的相同跨版本對照。
- 目前沒有這次下載過程的裝置記錄或更新前後檔案。既有撈珠失敗記錄只能證明當時遊戲／tweak 版本及戰鬥狀態，不能代替下載診斷。

分析對象為 PAD 日服 23.6.1／107553，UUID `38A9F704-C562-3BDD-B510-2112DAC084B0`，原版 executable SHA-256 `3ac8c5647e67694b5a3e68cf7049d3860f82f029a7e67f96477e9e2a3f490fd6`。本機重新計算雜湊一致。

被查的 Runtime、Badges、DeckPersistence、UnlockRestoration、Memory 及 PAD target 與已交付 0.5.36 的來源 `063f51a22c9c3e61a70681ac4e227f4ab5b333d1` 一致。之前撈珠修正的未建置變更保留，不拿它解釋已交付版的更新問題。

以下位址均為未加 ASLR slide 的原版 VA。本機唯讀分析輸出放在忽略的 `build/research/data-update-23.6.1/`，沒有將私人容器資料或完整反編譯加入來源。

## 已確認的程式行為

### 解鎖可以被原生存檔保存

[`PHApplyUnlocks`](../src/PHRuntime.m) 在通過遊戲、登入、帳號與設定檢查後，每秒維護 Skin／BGM 擁有位圖；必要時把 52-byte 條目內的 `flags` bit 0 設為 1。功能保持開啟時，沒有在原生序列化期間暫時移除這些改動。關閉後的還原只追蹤本次程序自己增加的 bits／flags，不能直接還原之前已存進磁碟的檔案。

[`PHBadges`](../src/PHBadges.m) 另改有效徽章的擁有位圖，不寫徽章參數表。[`PHDeckRestorer`](../src/PHDeckPersistence.m) 則會在登入／儲存後，把 matching 隊伍的 Skin、BGM 與徽章非預設選擇回蓋到記憶體。這些都不是直接寫 `.bin`，但其結果可以被原生保存。

| 資料 | Save 相對位移 | 寫入範圍／原生保存證據 |
|---|---|---|
| Skin owned | `0x5311D0` | 128 bytes；原生 writer 讀取 32 個 u32 |
| BGM owned | `0x5312D0` | 128 bytes；同一迴圈讀 Skin base + `0x100` |
| Badge owned | `0x52F31C` | 32 bytes；原生 writer 讀取 8 個 u32，保持原生編碼 |
| Skin／BGM entry flags | descriptor `0xC77398` 的 entries pointer，row + `0x0E` | 每次 2 bytes；尚未找到把此 heap 條目表存回資源檔的路徑 |

原生 `0x100443BD8` 建立版本 `0xB9` 的帳號／狀態存檔，讀取上述三份位圖及隊伍選擇，最後經 `0x1005EA358` 保存為 `data056.bin`。Skin/BGM 的迴圈另包含相鄰兩份 New 位圖；tweak 並沒有因此取得修改 New 位圖的權限。

`0x10044D034` 在下次啟動讀回這些資料。`0x10069D85C` 的成功登入解析會依伺服器資料重建擁有狀態，之後 tweak 才重新套用解鎖。因此，「移除 tweak」不會立即改回已保存的檔案內容，但後續原生登入仍可能重建相關狀態。

**這只證明本機保存的影響，不證明檔案損壞。** 原生 writer 對組好的獨立 buffer 重新計算校驗及編碼，位圖改動不會自行改變欄位長度。尚無證據顯示解鎖必然造成 checksum 不符、格式版本錯誤或資源版本被改壞。

### 沒找到直接修改更新檔案或下載內容的 hook

- Runtime 自己的設定與診斷存於 `Library/Application Support/PADHelper`。來源未找到針對 Documents 的 `.bin`／`048.bin` 讀寫、刪除或 filesystem 攔截；其他寫檔是本工具的策略／報告匯出。
- [`PHDataTask`](../src/PHRuntime.m) 只有主執行緒、`POST`、精確 `action=save_decks`、body 及 host/path 等條件符合才處理隊伍。其餘請求直接呼叫原 IMP，下載 response bytes 沒有被本模組修改。
- 原生 `-[cDOWNLOADER main]`（`0x10063831C`）用 sharedSession 送 `GET`。雖會經過同一個 NSURLSession 方法，仍在 tweak 的早期條件直接放行；沒有將它當成 save_decks。
- `PHWriteData` 只向既有可讀寫、非可執行記憶體寫入，沒有改頁面權限。已查到的解鎖目標不與下述資源版本及清單位址重疊。

### 資源更新有自己的保存與判斷路徑

| 原生函式 | 觀察到的行為 |
|---|---|
| `0x1004F0F1C` | 檢查 `data031.bin`／`data032.bin` 是否存在、清單是否載入，以及保存的清單來源字串是否與 API context 一致；另處理原生資料清理旗標 |
| `0x1004F1310` | 掃描 `mon2/`，依主／延伸清單計算待下載檔案及總 bytes |
| `0x1004F0C04`／`0x1004F096C` | 檢查檔案存在、大小及修改時間，也有清單旗標與原生資源選擇分支；尚未發現直接讀取上述解鎖位圖或 entry flags |
| `0x10063822C`／`0x100638110` | 將下載內容／解包結果寫入對應檔案，成功後設定清單指定的修改時間 |
| `0x1004F21D4` | 下載後重掃，清除完成旗標、校正時間，並保存兩份清單 |
| `0x1004F256C`／`0x1004F27C4` | 分別保存 `data031.bin`／`data032.bin`，資料來自主／延伸清單，不是 Skin／BGM 條目表 |
| `0x1005EF2DC` | 比較登入回應中的各種 catalog 版本與本機已載入版本，決定是否另抓卡片、技能等資料 |
| `0x1004533B8` | 啟動時載入各 bin；若讀回遊戲資料版本不等於 `23.61`，會使 `data030`／`031`／`032` 等重新建立 |

主／延伸清單 pointer 分別在 Save + `0xF5BDB0`／`0xF5BE38`，catalog 版本在 `0x531430` 起。Skin／BGM owned 的已查寫入範圍結束於 `0x531350`，沒有跨入版本欄位。

Skin／BGM 描述表由 `0x10045AA70` 從 resource 778 解析到新配置的 52-byte rows。原始載入 buffer 與 entry heap 是不同資料；解析結束釋放原 buffer。不能把「改 entry flags」直接等同「改下載檔或清單 checksum」。

### 單純延後到登入不構成修復

一般標題流程 `0x10028F940` 的 state 12 呼叫資源更新狀態機 `0x1005EFAA4`，完成後 state 13 才經 `0x1002891CC` 發出登入 request 33。登入後另有 catalog 更新流程。

目前 `PHRequestedMask` 已要求 `PHAccountReady`；新程序在觀察到成功登入前不增加解鎖位元。因此，若這次 25 MB 是登入前的資源更新，需優先區分上一輪保存留下的狀態、清單／檔案未持久化，以及 tweak 載入本身的影響。登入後仍可進入資料更新；現有 gate 也不等於「所有更新均完成」。

### 「下載完成」仍須核對實際保存

兩個原生行為已由反組譯核對：

1. `0x100638480` 收到 HTTP 200 後呼叫 `_storeDlData:`，但忽略其返回值，直接把傳輸標記成功。後續 `0x1004F21D4` 仍會重掃；不能說遊戲完全沒有檢查。
2. `0x100237270` 呼叫 `NSData writeToFile:options:error:` 後直接返回 1，沒有把寫入失敗傳回上層；此 helper 用於上述 native bin 保存。設定檔案時間的 `0x1002364C8` 也沒有回傳 `setAttributes` 的實際成功值。

這能解釋為甚麼調查必須檢查檔案是否真的保存，**並不證明使用者當時發生了寫入失敗，也不證明 tweak 造成了它**。

## 尚未確認的因果關係

目前最有理由先隔離的是解鎖及本地選擇保存，因為使用者在開啟至少一項解鎖時能復發，且有實際進入原生存檔的路徑。但沒有同環境、僅切換解鎖的對照，還不能排除載入時的 hook、容器行為或原生更新持久化問題。

也不能只根據約 25 MB 的大小判定是哪種資料：它可能是 `mon2/` 的一組資源，或登入後的 catalog 更新。清除多份 bin 可同時重建清單、版本與帳號快取，不能由這次清理效果指定某一檔為壞檔。

## 下一個可辨識的對照

以下是待執行步驟，**本輪沒有代為操作或取得結果**：

1. 保留現有檔案與同一個容器。tweak 照常載入，PC 面板只關閉 Skin、BGM、徽章三項解鎖，確認面板顯示關閉；依賴 BGM 解鎖的附加選曲亦會停止生效。其他設定與條件不變。
2. 如仍要求下載，完成這一輪並進入主畫面，讓原生登入有機會重建帳號狀態，再完整離開、重開兩次。第一輪可能仍受之前保存狀態影響，不能只看第一次是否下載。
3. 如果此後穩定，再每次只開回一項解鎖，記錄完成登入及下次重開的結果；不同時改容器、刪 bin 或升級版本。如果三項全關仍重複，暫不歸因於特定解鎖。
4. 若需追加診斷，優先記錄更新提示發生在登入前／後、PC 的 accountReady／activeMask，以及 `data031.bin`、`data032.bin`、`data056.bin` 的存在／大小／mtime 與 `mon2/` 被判定缺失／大小不同／時間過舊的檔案數。內部亦須記錄 bin 載入、寫入及設定 mtime 的實際結果。

診斷資料只需要原因與檔案摘要，不收集 `048.bin`、token、帳號內容或完整請求。不以 `data056.bin` 的整檔 hash 改變判定損壞：它含正常變動資料，且保存編碼會帶入可變值。現有「複製診斷」沒有資源更新細節；上述追加欄位尚未實作。

在辨識原因前，不直接替換 `.bin`、強行修改版本／checksum、略過原生下載檢查或自動清理容器。若後續證明需要隔離解鎖與原生保存，應另行設計、驗證保存前後的原生狀態與本地選擇，再依分批流程安排編譯測試；不能把暫時關開解鎖當成已驗證修復。
