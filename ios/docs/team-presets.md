# 整隊、武器與滿狀態：原生資料分析

2026-10-27；日服 iOS PAD 23.6.0／106878。此文件回應使用者提出的六個位置、武器、Lv.120、普通覺醒全開及加值 +891。**這些整隊設定尚未納入 `0.3.1-battle`；該版交付的是關卡分類 1 的判斷修正。**

## 目前為何只有一名

`PHBattleSession` 只保有一個作用中位置及一份原始形態，`PHBattleNative` 使用普通變身流程修改 `M+0x118` 後重建該位置。它刻意沿用來源的等級、繼承與部分附加資料；這個介面沒有六組本體／武器配方，也沒有滿狀態的資料來源。限制來自目前的實作範圍。

整隊操作需要六槽設定與批次提交／還原，並處理部分位置失敗、隊長交換、原生再次變身及切樓層後的重建。武器和狀態還需要一個在原生重建時持續有效的參數來源。直接把最後算出的數值改滿，之後仍會被來源資料重新計算。

## 已確認的規格

| 項目 | 原生依據與設定規則 |
|---|---|
| 六個位置 | 一般單人隊員為六個 `0x5F0` 記錄。圖鑑編號與持有卡片識別碼分開，六組配方需各自保存本體、武器及還原身分。 |
| 本體 Lv.120 | `0x1005318D8`、`0x1002410F0` 會檢查怪物參數 `+832` 的限界突破條件；支援時最高 120，不支援時採 `+20` 的原生等級上限。 |
| 普通覺醒全開 | 依怪物參數 `+748` 起的有效覺醒表計數，最多十項；不以固定填 10 取代實際數量。 |
| 技能等級 | 依技能表、52-byte 記錄的 `+14` 取得最大技能等級。技能等級與目前戰鬥中的技能充能是不同欄位。 |
| 本體 +891 | 原生 `0x1002410F0`／`0x100049BEC` 明確以 891 為總加值上限；對應的三個儲存 bytes 為 `C6 C6 63`（198、198、99）。這是遊戲的壓縮格式，不能把三個 297 直接塞進 byte。 |
| 武器 | 原生另傳入八個 bytes 的繼承參數，包含圖鑑 ID、覺醒數／滿加值標記、等級、技能等級及形態資料；武器也依自身參數決定等級上限。此結構的加值使用滿加值標記，不能把本體的 +891 儲存格式直接套到同一位置。 |
| 超覺醒／潛覺 | 有獨立選擇與槽位規則；普通覺醒全開不會自動指定這些欄位。 |

`0x1005A12F0` 呼叫 `0x1004844C8` 建構衍生資料。後者實際有九個參數：包含本體附加資料、戰鬥條件、地下城規則及獨立的繼承參數；最後一個參數由 stack 傳入。只依較早的七參數反編譯呼叫文字實作會漏掉武器資料，已用 ARM64 指令交叉核對。

## 後續需要接上的來源

原生已有關卡指定隊員：`0x10059A848` 解析 `param` 與 `assist`，十個 `0x2C` 參數槽可以描述本體／武器／狀態，`0x1005A12F0` 再使用該資料重建。然而 `0x100594CC8` 只在找到該關卡的 `st_<id>.txt` 時建立腳本環境，找不到時會把資料指標設為 0。一般地下城不能假定這個環境存在，也不能填一個虛構指標來啟用。

因此完整版本需選定並實作適用於一般關卡的參數來源，確保六名隊員在回合推進、重新計算、換樓層及還原時都使用一致的本體／武器資料。滿狀態建構的原生格式已確認，普通關卡的持續注入來源及六槽交易尚未實作／真機驗證。

## 分類 1 的修正依據

`S+0x5C90C0`（原診斷 `mode`）由 `0x10028A734` 保存入口分類，`0x1005B6488` 又依分類做正規化。單人隊員選取、摘要及隊伍刷新實際分流使用另一個多人欄位。`0.3.1-battle` 允許已核對的分類 0／1，仍要求 source 0、multi 0、phase 2、輸入空閒及全部既有一致性檢查；沒有修改遊戲保存的分類數值。
