# 三人模式入場修正

`0.4.4-entry`；日服 PAD 23.6.0／106878。修正範圍為 mode 7／multi 1，包含兩人及三人入場。使用者確認 0.4.2 的 host 自動替換成功，guest 則在輪到自己時看到原隊伍；新版處理後者的同步覆蓋。

0.4.4 另加入本機隊伍的入場 HP 初始化及逐 frame 綁定監測。最大 HP／其他隊伍數值已由原生 refresh 更新；新增的目前 HP 初始化只在新入場執行，補回仍保留同步後傷害。詳見 [入場數值與時機](entry-derived-state.md)。

## 原因與行為

舊版把新的入場限定在 phase 0。原生建構流程會先將 multi 1 設為 phase 46，同步完成後才進入 phase 0；因此排程在首次讀到 phase 46 時就被取消。phase 2 同時用於本機操作與其他玩家的回合，不能單憑它允許手動替換。

新版在 wave 0、非恢復、回合計數 0 且開場旗標通過時，接受 mode 7 的 phase 46。隊伍陣列暫未就緒時保留排程，輸入仍須放開。依本機連線席位選擇自己的六人 bank，使用既有原生配方／SB 交易，並在同一 frame 恢復原本畫面。回合計數從不改寫。雙向切換均使用已驗證指紋的原生 loader，不直接偽造 currentTeam。

選擇前後驗證每個 bank 的角色、充能與 HP，完整交易成功後再次驗證其他隊伍未被改動、原畫面與 HP 已回復，以及本機 provider 的所有權。回復失敗時停止後續寫入。自己的隊伍可在畫面外保留租用，還原等待自己的操作回合；借看自己的隊伍不會取得操作權。

不會在 phase 2 補做 SB 重置，以免抹去先制延遲。單人 phase 0 的成功流程保留。使用者於 2026-10-28 已確認單人入場與 SB 成功。

## guest 換回合同步

`0x10001771C` 依接收快照重寫每一隊的成員狀態，再呼叫 `0x100019BBC` 和 `0x10006F798` 重建。每名隊員的 `+0x128` 腳本綁定來自快照成員的 byte 22，充能 `+0x1c8` 來自 byte 38 的 uint16；本機租用的 44-byte 配方並不在這個同步資料內。phase 48 的 `0x10001B6A4` 會在換回合時呼叫此流程，並非只在開場發生。這能造成「入場已套用」後又失去本機 provider token。

新版成功入場後，記住本機席位、隊伍陣列與六份既有配方。綁定遺失時，僅在 context／配方仍屬本機、原隊員來源與本體／武裝相同、原生綁定未指定（0 或 -1）、參數未被任何成員引用時標記 `rebindToken`；不將它當成已生效的 `providerToken`。原生新腳本、不同來源、參數改寫、席位或拓樸變更均不補回。

補回只在自己的 phase 2、自己的隊伍畫面、無觸控／拖珠且無暫時變身時執行。重用原有參數與 token，不配置新的紀錄；一次交易完成全部待補位置。每一位置沿用同步後的原生變身與充能，只按新技能上限裁切，並重建 HP／隊員摘要校驗。**補回不重新發放入場 SB**；同步端傳回的充能可能與入場 SB 計算後不同，面板 `last SB` 不代表目前充能。

失敗時回復已動過的所有綁定、同步後充能及 HP，保留原生異常旗標；無法確認完整回復時停止後續寫入。同一回合不循環重試，session 在失敗後停止自動補回。等待時可取消／還原，或關閉自動入場；若原生綁定已被同步解除，還原只歸還未被引用的本機參數，保留遊戲目前的等級、變身與充能。已生效的其他位置仍走一般還原流程。

診斷新增本次入場的 `applied / lost mask / rebind waiting / rebound members`、首次觀察每次遺失的 phase／serial，以及每名隊員的 script／provider／rebind。程序累積的入場次數不再是唯一證據。

## 原生依據

以下 VA／offset 來自同一份已校驗遊戲映像。沒有將使用者的完整裝置診斷加入 repo。

| 位置 | 用途 |
|---|---|
| `0x1005b6488` | 建構所有隊伍、逐隊計算初始 SB，multi 1 最後設為 phase 46 |
| `0x10001afb8` | phase 46 同步完成後轉入 phase 0 |
| `impl + 0xa3e48` | 回合計數；取隊伍數的餘數得到回合擁有者 |
| `impl + 0xa3e4c` | 本機連線席位；`0x10000be9c` 從本機連線記錄初始化 |
| `impl + 0xa3e58` | 畫面載入的隊伍，可能因預覽／原生 refresh 暫時改變 |
| `impl + 0xa3e5c` | 共用隊長／助人的來源選擇，不是本機席位欄位 |
| `0x10060d1f0` | 原生 phase 2 對照回合餘數與本機連線席位 |
| `0x10000cee0` | 載入選定隊伍及其 HP；新增 64-byte 指紋 |
| `0x100019ff0` | 保存本隊 HP 到 bank + `0x6c48`，設 descriptor bit 4 |
| `0x10001771c` | 接收快照逐隊重寫 script 綁定、變身、充能等欄位，之後重建隊伍 |
| `0x10001b6a4` | phase 48 換回合時採用快照，再切換回合擁有者 |
| `0x1005a12f0` | 綁定大於 0 且 script program 存在時才使用對應的 44-byte 配方 |

## 驗證範圍

模型／session／原生記憶體 fixture 測試涵蓋兩個、三個六人 bank、每個本機席位、phase 46 等待、觸控釋放、正確一次性套用、畫面外租用、自己的首次回合、遠端回合及預覽、先制延遲保留、恢復／取消／中途啟用排除。故障注入包含後續隊員重建、充能／HP／指紋、席位變更、隊伍 loader、無關 bank 汙染及失去入場視窗。原有單人 SB 計數／上限與 GUI 回歸測試繼續執行。

原生重建失敗但尚未發布至 bank 時，交易內的還原讀取只允許本次改寫的單一位置與 bank 暫時不同，且 bank 必須仍等於改寫前快照、席位／身分及 provider 必須一致。正常讀取與其他位置仍保持嚴格比對；完成還原後再驗證所有 bank。

0.4.3 的 fixture 另模擬 peer 快照清除綁定、重建回原生來源及同步充能，覆蓋 host 後續回合與每個 guest 席位、連續多次補回、原生變身／充能上限、無新配置、未綁定時取消、預览與觸控／暫時變身等待、來源或 context 改變拒絕、失敗全批次回復及原生異常旗標保留。這比僅複製 bank 的切換替身多驗證了實際失效條件。

測試工具的原生函式為替身；靜態分析與 CI 不等同真機多人遊戲、技能效果或伺服器結算驗證。
