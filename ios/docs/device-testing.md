## 0.4.3-entry：guest 同步後補回

2026-10-28，使用者回報 `0.4.2-entry` 作 host 時自動替換成功，guest 時不成功。提供的狀態為本機第 2 隊／回合第 2 隊／serial 1，顯示「遊戲接管」，同時程序累積計數有一次六人套用及 SB 19。這些累積計數不足以單獨證明本次 guest 套用時機，因此新版另記錄每次入場的結果及綁定遺失時機。完整裝置診斷未加入 repo。

| 情境 | 核對 |
|---|---|
| guest 第 2、3 席首次自己的回合 | 放開觸控後，自動補回六人；`rebound members` 增加，`rebind waiting` 歸零 |
| 連續數次輪到自己 | 後續同步若移除綁定仍可補回，沒有參數耗盡；`Automatic entry count` 不再增加 |
| 先制延遲、技能已用、原生變身 | 保留同步後充能及變身，補回不重發 SB；核對實際技能／武裝效果 |
| 別人的回合／預覽自己的隊伍／觸控未放開 | 等待，沒有補回或改變其他隊伍 |
| 等待補回時取消或關閉自動入場 | 自己的回合釋放保留的配方，遊戲同步後的等級／充能不倒退 |
| 單人及 host | 入場自動替換與 SB 維持既有成功行為 |

`Current entry: applied` 表示本次身分確實完成過入場交易；`lost mask`、`rebind waiting`、`rebound members` 與 `Last binding loss` 均按入場重設。`script / provider / rebind` 分開表示原生綁定、已生效的本機配方及待補回配方。`last SB` 只代表入場計算結果，不能證明 peer 同步後保留同樣充能。真機及結算未由 CI 模擬。

## 0.2.1-gui：儲存與重啟

新版加入保存／伺服器接受／回蓋狀態，並修正新儲存未需預設化或本地保存失敗時，舊交易仍可能回蓋舊選擇的情況。更新只替換 dylib，保留原有 config.json 和 account 檔。

在同一 guest 容器、同一帳號進行：

| 次序 | 操作 | 通過條件 |
|---|---|---|
| 1 | 選一個非預設 Skin 和 BGM，儲存一次隊伍 | 面板本機保存次數增加，伺服器接受次數增加，遊戲沒有儲存錯誤；同一交易解析成功後顯示回蓋結果 |
| 2 | 完整關閉遊戲，再從 LiveContainer 啟動並登入 | 同一隊的 Skin／BGM 保留；面板顯示登入後的本地選擇讀取及回蓋結果 |
| 3 | 把同一隊的 Skin／BGM 改回預設，儲存，再重啟 | 保持預設，不被舊選擇回蓋；面板可顯示「此請求無需預設化」，這是正常結果 |
| 4 | 分別只開 Skin、只開 BGM | 各功能只影響自己的欄位；未啟用欄位依既有保存規則保留 |
| 5 | 在請求還未完成時再改選擇並儲存 | 舊 completion 不更改最新回蓋；若交易無法唯一對應，面板顯示等待重新登入，不猜測立即恢復 |
| 6 | 有條件時測試次要隊伍 bank | 同 bank、同 slot、同隊伍且數量一致時正確保存／恢復 |

第 1 步的「伺服器接受」只計算這份 dylib 修改並追蹤的 save_decks 請求，條件是 HTTP 200 且 JSON res=0；不表示其他 API action 已驗證。改回預設而沒有 request 改寫時，接受計數可維持不變。

回蓋只覆寫同隊的預設欄位，現有非預設選擇會保留。正在編輯、隊伍數量／身分不匹配或原生解析失敗時，會顯示跳過原因。

計數是本次程序的觀察值，重啟會歸零；主要／次要隊伍數來自目前登入帳號的有效本地檔。面板「複製診斷」可用於回報異常，內容不含帳號 ID、query、憑證或隊伍內容。
