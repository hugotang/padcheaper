## 待建置：3 人兩位隊友斷線後單人續玩

1. 日後新版本先進 3 人，兩位隊友斷線／退出變灰，等待原生切換完成。盤面已能手動轉珠時，應顯示「3 人協力・單人續玩」並恢復「轉一次」；切換中、彈窗未結束或手指未放開時仍停用。保留收合狀態，不自行轉珠。
2. 確認診斷為 mode 7／selector 2，`continuationOwnerKnown=true`、`localReady=true`、`timeSource=move-timer`；線上倒數未確認或連線值為 0 不應單獨阻擋。首次真機需核對實際 `teamCount`、`localSeat`／`viewTeam`、`localStatus`、`networkFlags`、`syncState`／`syncStep`、`recoverySource`／`recoveryFlags`、`continuationDialog`，因原紀錄在這些欄位讀取前失敗。
3. 按一次，完成一條路徑並放手；下一盤再次明確點擊才轉。隊長模式應保持本機隊長／助人來源；也用高 Combo 區分讀盤與隊長條件。連續、自動技能與套隊仍停用。
4. 分別檢查自己在各席位、他人回合斷線、只剩兩席後再斷線、求路／持珠中切換。舊工作必須取消，原生清理後按鈕可恢復；不得把舊放手或路徑送到新窗口。背景恢復、結算、彈窗或原生 recovery 未完成時繼續停止。
5. 不重啟 app 結束續玩，進新 3 人及 4 人，重驗 0.5.14 的跨場次流程。如果仍停用，在可手動轉珠當下複製 `readReason`、`onceReadiness` 及歷史；新增彈窗範圍錯誤可與核心記憶體錯誤分辨。

原生證據與限制見 [續玩研究](../research/orb-multiplayer-solo-20261031.json)。以上是待驗收項目，不能視為已修復的真機結果。

## 待建置：轉轉＋光 T／心四連搜尋比較

新增 5×4 密集雙色盤及猛毒政策案例均未跑；[密集盤面研究](../research/orb-dense-spinner-20261031.json) 是源碼推導，並非新版本執行結果。

1. 明確建置後先執行記錄盤面的 solver 案例及獨立六相位 oracle。舊預覽路徑應維持拒絕；新版達標路徑必須同時滿足光 T、心四連、危險珠及原步數上限，不能只驗證當下顏色。
2. 用 [比較腳本](../research/orb_spinner_search_benchmark.py) 對原四盤加新六格轉轉盤共五盤交替跑舊／新 probe，各至少五次，維持 800 ms／48 步／beam 512；使用 `--policy-input` 保留各盤斜轉／優先設定。比較每盤達標次數、耗時中位數、步數、Combo、`evaluationCalls`／`evaluationCacheHits`；舊版成功的三盤亦需核對有無退步。
3. 重新跑既有 6×5／7×6／5×4、荊棘、毒、封條、珠數不足、轉轉相位、取消與逾時案例。快取不得混用不同輪次／目標或把接觸傷害套到另一條路徑；session 最終驗證保持不經快取。
4. 真機再觀察相近轉轉盤面的達標與等待時間；桌面效能不能直接代表 iPhone。這次原紀錄的 714 ms／162,618 候選只作舊版觀察，尚無新版加速或成功率結果。
5. 5×4 的 12 光 8 心＋右下轉轉應回報珠色比例不相容且不開始 beam search；測八格固定分隔的邊界見證及改為 Combo 後能重新求路。六格轉轉盤仍以有界搜尋和六相位結果判斷，不可直接報無解。
6. 已開啟 `allowPoisonWithHeartFour` 的策略，首消心四連時毒及猛毒皆可消，邪魔及首消全清爆彈可同盤出現。開關關閉、沒有心四連、心五連、只靠後續落珠成四連、心不可消，或任一轉轉相位缺心四連，均不得借此放行毒／猛毒。核對排序不再為了避猛毒犧牲已允許的目標／Combo。
7. 核對設定開關與策略匯入／匯出說明明示「毒／猛毒」，原 true／false 正確保留，忙碌中不得改政策；搜尋與放手診斷仍分開記錄毒總數及猛毒最大數。混合荊棘時沿用目前 HP 大於路徑傷害的原限制，不預支心四消回復。

## 0.2.1-gui：儲存與重啟

新版加入保存／伺服器接受／回蓋狀態，並修正新儲存未需預設化或本地保存失敗時，舊交易仍可能回蓋舊選擇的情況。更新只替換 dylib，保留原有 config.json 和 account 檔。

在同一 guest 容器、同一帳號進行：

| 次序 | 操作 | 通過條件 |
|---|---|---|
| 1 | 選一個非預設 Skin 和 BGM，儲存一次隊伍 | 面板本機保存次數增加，伺服器接受次數增加，遊戲沒有儲存錯誤；同一交易解析成功後顯示回蓋結果 |
| 2 | 完整關閉遊戲，再從 LiveContainer 啟動並登入 | 同一隊的 Skin／BGM 保留；面板顯示登入後的本地選擇讀取及回蓋結果 |
| 3 | 把同一隊的 Skin／BGM 改回預設，儲存，再重啟 | 保持預設，不被舊選擇回蓋；面板可顯示「此請求無需預設化」，這是正常結果 |
| 4 | 分別只開 Skin、只開 BGM | 各功能只影響自己的欄位；未啟用欄位依既有保存規則保留 |
| 5 | 在請求還未完成時再改選擇並儲存 | 舊 completion 不更改最新回蓋；若交易無法唯一對應，面板顯示等待重新登入，不猜測立即恢復 |
| 6 | 有條件時測試次要隊伍 bank | 同 bank、同 slot、同隊伍且數量一致時正確保存／恢復 |

第 1 步的「伺服器接受」只計算這份 dylib 修改並追蹤的 save_decks 請求，條件是 HTTP 200 且 JSON res=0；不表示其他 API action 已驗證。改回預設而沒有 request 改寫時，接受計數可維持不變。

回蓋只覆寫同隊的預設欄位，現有非預設選擇會保留。正在編輯、隊伍數量／身分不匹配或原生解析失敗時，會顯示跳過原因。

計數是本次程序的觀察值，重啟會歸零；主要／次要隊伍數來自目前登入帳號的有效本地檔。面板「複製診斷」可用於回報異常，內容不含帳號 ID、query、憑證或隊伍內容。
