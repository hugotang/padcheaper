## 0.2.1-gui：儲存與重啟

新版加入保存／伺服器接受／回蓋狀態，並修正新儲存未需預設化或本地保存失敗時，舊交易仍可能回蓋舊選擇的情況。更新只替換 dylib，保留原有 config.json 和 account 檔。

在同一 guest 容器、同一帳號進行：

| 次序 | 操作 | 通過條件 |
|---|---|---|
| 1 | 選一個非預設 Skin 和 BGM，儲存一次隊伍 | 面板本機保存次數增加，伺服器接受次數增加，遊戲沒有儲存錯誤；同一交易解析成功後顯示回蓋結果 |
| 2 | 完整關閉遊戲，再從 LiveContainer 啟動並登入 | 同一隊的 Skin／BGM 保留；面板顯示登入後的本地選擇讀取及回蓋結果 |
| 3 | 把同一隊的 Skin／BGM 改回預設，儲存，再重啟 | 保持預設，不被舊選擇回蓋；面板可顯示「此請求無需預設化」，這是正常結果 |
| 4 | 分別只開 Skin、只開 BGM | 各功能只影響自己的欄位；未啟用欄位依既有保存規則保留 |
| 5 | 在請求還未完成時再改選擇並儲存 | 舊 completion 不更改最新回蓋；若交易無法唯一對應，面板顯示等待重新登入，不猜測立即恢復 |
| 6 | 有條件時測試次要隊伍 bank | 同 bank、同 slot、同隊伍且數量一致時正確保存／恢復 |

第 1 步的「伺服器接受」只計算這份 dylib 修改並追蹤的 save_decks 請求，條件是 HTTP 200 且 JSON res=0；不表示其他 API action 已驗證。改回預設而沒有 request 改寫時，接受計數可維持不變。

回蓋只覆寫同隊的預設欄位，現有非預設選擇會保留。正在編輯、隊伍數量／身分不匹配或原生解析失敗時，會顯示跳過原因。

計數是本次程序的觀察值，重啟會歸零；主要／次要隊伍數來自目前登入帳號的有效本地檔。面板「複製診斷」可用於回報異常，內容不含帳號 ID、query、憑證或隊伍內容。

## 0.3.0-battle：新功能驗收

徽章解鎖已收到真機通過回報；其餘項目及徽章保存／邊界情境尚待驗收：

| 功能 | 操作 | 核對 |
|---|---|---|
| 換怪 | 原隊伍進一般單人關卡，選一名隊員及有效圖鑑 ID，套用並還原 | 圖像、技能、充能、覺醒、HP 與隊伍數值；摘要一致；其他隊員不被替換 |
| 換怪邊界 | 暫時變身、原生再次變身、隊長交換、切樓層、關閉開關與離開地下城 | 等待合適時機還原，或明確使過期記錄失效；不覆寫遊戲新狀態 |
| 徽章解鎖 | 使用者實機測試 | **使用者回報通過**；沒有據此擴大認定所有保存／重啟及帳號邊界也已通過 |
| 徽章 | 開啟徽章、選非預設 ID、儲存並重啟，再改回 0 重試 | 有效數量、原生選擇可用、交易成功與按 bank 回蓋；預設不被舊值覆蓋 |
| 徽章邊界 | 關閉功能、重新登入、換帳號 | 僅移除新增 ownership bits；原合法擁有資料及帳號隔離正確 |
| 計時 | 一般單人倒數關卡切後台再返回 | 暫停修正次數、實際倒數與畫面正常；沒有自動跳轉階段 |
| 手動撤窗 | 計時退出彈窗已出現時按面板按鈕 | 顯示一次手動撤窗並返回操作階段；正常提示窗、其他模式、過期點擊保持不可操作 |

換怪及撤窗的本地成功不能證明通關、排行或獎勵會被伺服器接受。結算結果需另行回報與驗證。新版診斷會包含隊員圖鑑編號及充能，不包含帳號 ID、入場 hash、query 或憑證。

## 0.3.1-battle：關卡分類 1

使用者在 `0.3.0-battle` 回報換怪顯示「此入口尚未支援（mode 1／source 0／multi 0）」。`mode` 對應 `S+0x5C90C0` 的關卡分類，並非多人旗標；實際多人狀態位於另一個欄位。`0.3.1-battle` 讓已核對的分類 0／1 使用相同單人檢查，並同步修正計時控制的分類判斷。source、multiplayer、phase、HP／隊員摘要及原生函式校驗繼續逐一檢查。

重新進入相同關卡後，應不再被 `mode 1／source 0／multi 0` 這一項阻擋；後續若顯示其他等待／停用原因，仍須按當時診斷判讀。解除這個判斷錯誤尚不代表實際換怪已在裝置上通過。整隊、武器及滿狀態的擴展分析見 [整隊與滿狀態](team-presets.md)。
