# 0.5.41 求路執行緒閃退調查

2026-11-07 的兩份閃退報告均顯示 `PADCheaper.dylib` 在求路執行緒釋放記憶體時，被系統記憶體配置器以 `SIGABRT` 終止。來源審查已確認 `SelectBeam` 有一個可越界的色彩分桶索引；這是需要修正的記憶體安全缺陷，但目前不能證明它是這兩次閃退的唯一原因。

## 已確認的來源缺陷

[PHOrbSolver.cpp](../src/PHOrbSolver.cpp) 的 `ColorGuidance` 先將 `weakestColor` 設為 `PHOrbBasicTypes`，即 **6**，表示沒有待補的顏色。候選已達成色彩目標、仍有 Combo 等其他目標未滿足時，這個值可以保留到 `SelectBeam`；它不是只能出現於 0–5 的普通顏色索引。

舊版色彩分桶鍵為：

```cpp
missingColors | (unsigned(weakestColor) << PHOrbBasicTypes)
```

但 `head`／`tail` 只按目標桶配置 **64 × 6 = 384** 格，有效索引為 **0–383**。當 `missingColors == 0`、`weakestColor == 6` 時，分桶鍵是 **384**，因此 `head[384]`、`tail[384]` 已越界。此後若讀出的 `tail` 被用於 `link[tail[bucket]]`，也可能進一步造成堆積記憶體損壞。這一推導可從交付來源直接確認，不需要把閃退位置當作越界指令。

## 二進位位置與因果界線

主調查以 IDA 讀取交付 dylib 的副本，核對 `SelectBeam` 範圍為模組偏移 **`0xd4320`–`0xd56d4`**。報告記錄的 `0xd5444` 是呼叫返回位置；前一條 `0xd5440` 的 `operator delete` 位於區域變數 `layouts` 的 `unordered_set` 桶陣列釋放流程。

這與「先前記憶體受損，到釋放時才被配置器偵測」相容，但釋放位置不是已觀察到的越界現場。沒有當時索引、原盤或 sanitizer 報告，故不宣稱已定位兩次閃退的首次破壞指令，也不排除其他記憶體問題。

## 修正與待驗證

來源修正保留原目標桶 **384** 格，另將色彩桶明確設為 **64 × (6 + 1) = 448** 格，`head`／`tail` 容量取兩者較大值。第七個色彩區間容納「沒有缺色」的保留值，原分桶鍵、候選排序、保留比例與輪流取候選方式均維持原意；不以強制把 6 改成某一種珠色來掩蓋問題。

手動測試入口 `ios/test.sh` 已加入 ASan＋UBSan 版本的內部引導／候選選取套件，三份 C 模型與 C++ 套件均帶記憶體檢查，使用獨立物件檔；錯誤會立即使測試失敗。這樣下次測試能在首次越界讀寫處報錯，不必等到釋放記憶體才發現損壞。

[新回歸案例](../tests/orb_beam_bucket_tests.inc)以六色橫列及合法等色拖路取得真正評分，涵蓋六色已滿、五色＋心已滿、只有 Combo 未滿，以及四轉轉六相位。案例直接將超過保留數量的候選送進 `SelectBeam`，檢查候選身分、數量、不重複、排名保留、多樣性及丟棄候選集合；另涵蓋原本不使用分桶的小量／全保留分支。這些是可重現保留值 6 的合成案例，並非兩份 crash 的原盤。

目前完成報告、來源及交付二進位位置核對，以及 solver、主案例、內部引導案例三份 C++17 嚴格 syntax-only 檢查、兩份 shell 語法、研究 JSON 與文件連結檢查；未產生物件檔。**本批尚未建置產品、執行測試或產生新交付檔**。待使用者明確要求編譯測試後，需執行新增案例、sanitizer 檢查及相關回歸，再以新版真機確認。沒有原盤，離線驗證通過也不能稱為兩次原始閃退已完整重現並排除。
