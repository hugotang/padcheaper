## 本次停止原因

原紀錄為 PAD 23.6.1、6×5、八方向、48 步／beam 512／800 ms；零起點限制、無封條／荊棘／不可消，每組至少三顆。唯一未鎖轉轉在零起算格 6，六色循環，15 frames／30 fps，每圈三秒，原生剩餘 19 秒。

目標為首消光 T 一組、心四連一組及至少 9 Combo。敵人條件需要 15，已計隊長 +2／助人 +4，不能再重複計入這六個加算或自行降低九個首消要求。

普通、撈光、撈心三次均為 `insufficient-orbs`、0 個候選、0 個搜尋 pass、0 ms。這次沒有進入 beam search，不能歸因於 800 ms 太短；前批針對逾時候選的重試也不會解除此珠量拒絕。

只保留匿名顏色與限制，私人原始紀錄不納入來源。色碼為火 0、水 1、木 2、光 3、暗 4、心 5：

```text
1 3 3 5 5 3
3 3 5 0 3 5
4 5 0 3 3 3
5 3 0 5 3 5
4 1 5 2 5 5
```

29 顆非轉轉珠的數量為 `[3,2,1,10,2,11]`。取色 `t` 後，最後留回轉轉的一顆固定珠 `d` 不再留在盤外；放手色序為 `p` 時，庫存必須是 `fixed - e[d] + e[t] + e[p]`，仍只有 30 顆。同一路線的 `d` 必須固定，不能每個色序各選不同的犧牲珠。

| 取色 | 忽略形狀與路徑、但要求所有放手色序的 Combo 上限 |
|---|---:|
| 火 | 7 |
| 水 | 8 |
| 木 | 7 |
| 光 | 7 |
| 暗 | 8 |
| 心 | 8 |

各欄先對每個固定的 `d` 取六相位最低 `sum(floor(count[color]/3))`，再取最佳 `d`，並保留不取色的普通分支。上限不代表能排成該數量的 Combo；本盤任何單次取色均低於九。

更進一步，光 T 五顆、心四連四顆，加其餘七組最少三顆，合計恰好 30 顆。要首消九組，全部珠都必須在第一波消除，除指定兩組外只能是三顆群組。因此光珠總數必須餘 2、心餘 1、其他色餘 0（除以三）。一格未鎖六色轉轉變色就改變兩色的餘數，不能讓所有相位都符合。**在轉轉仍未鎖定且要求六相位都成功的前提下，單純增加取色次數也不能消除此衝突。** 此論證不涵蓋鎖珠技能、指定放手相位、天降或其他遊戲操作。

即使允許指定放手相位，原本五種顏色的固定珠餘數不符合上述必要條件；一次交換最多改兩色，再加放手相位的一色，仍不夠。因此這盤在數量上至少需要兩次交換。例如先把一顆木換水，再把一顆心換暗，固定珠變成 `[3,3,0,10,3,10]`；最後轉轉為光，總量為 `[3,3,0,11,3,10]`，才容得下光 T＋兩組光三連、心四連＋兩組心三連、火／水／暗各一組三連，共九組。這只是未考慮排列與路徑的庫存見證，**不是可執行路線**，沒有證明原生連續交換、等待及滿盤布局在時間內可達。

## 本批來源修改

- [PHOrbSolver.cpp](../src/PHOrbSolver.cpp) 的必要珠量檢查由「只加一顆」改為包含普通分支及各種合法單顆交換；每一種交換須同時通過全部相位、全部目標。回收的珠色限於轉轉色表內，保留唯一未鎖轉轉驗證。固定珠數不代表供珠或實際路徑可達，檢查仍只作必要條件。
- 新增 `PHOrbPlanFishing`：有 Combo 目標便檢查所有色表顏色，不再只讀形狀的 colors mask。先排除不可能的交換，再依形狀缺珠及跨相位 Combo 上限排序，最多選兩色。純 Combo 也能進入既有單次撈珠 fallback；仍可能因兩色限額或 beam 裁剪漏掉其他解，未宣稱完整搜尋。
- 去重的 `Hash` 及布局多樣性的 `LayoutKey` 納入 `Node.fished`。相同盤面、末格及前一格，尚未進入／已進入轉轉的後續合法動作不同，不能當成同一狀態。普通未撈珠的 key 保持原值；評分 cache 仍按盤面共用，因為消除評分不取決於是否已用掉入口。
- [PHOrbSession.mm](../src/PHOrbSession.mm) 在普通搜尋失敗後，於 worker 完成取色規劃。`fishingPlan` 分開記錄選色、珠量拒絕、兩色上限及各色 Combo 上限；只有真的呼叫求路器才記入 `candidateAttempts`。前批安全候選保留／逾時重試接續使用。
- [失敗訊息](../src/PHOrbFailurePresentation.inc) 同步單顆交換檢查。若全部取色因庫存被擋下，本次可顯示「已檢查六色、只撈一顆且全部色序成立的珠數上限八、尚未進入撈珠搜尋」，保留原本的九 Combo／敵人加算解釋。

本批不擴大撈珠操作：仍限單人、一格未鎖轉轉、沒有荊棘、已知有效倒數及足夠移動時間；只允許一次入口，預留一整圈等待。重播、每步原生盤面核對及 `goalsMet && hazardsSafe` 執行門檻維持。沒有增設多人 Auto、技能操作、計時器／珠色寫入或自動重開戰鬥。

## 下一批：雙次取色與判定色序的離線模型

使用者要求「下一步」，新增 [PHOrbTimedFishing.h](../src/PHOrbTimedFishing.h) 與 [PHOrbTimedFishing.inc](../src/PHOrbTimedFishing.inc)。結果使用獨立的 `PHOrbTimedFishingRoute`，沒有 Session／原生呼叫者，也不轉成可提交手勢的 `PHOrbRoute`。`Solved` 只表示路線已在本機模型完整重播，且在指定消除判定色序下達標；不能據此宣稱可在手機執行。

- 珠量枚舉允許零至兩次交換，每次先扣一顆實際存在的犧牲色，再加入取色，最後加入轉轉的判定色。T／L／十字／正方形／四連等單色精確形狀先保留所需珠數，再算剩餘 Combo 上限。一般消除、橫排、直排與多色目標可能共用群組，不重複保留；珠量通過仍不是布局可達證明。
- 最多保留八個方案，先按較少交換、較高 Combo 上限及供珠距離排序，替每個判定色保留一個方案後填餘額。每個方案做獨立 beam 搜尋，分用同一總時限；去重包含已進入次數，beam 另保留不同交換進度。兩次／八案／beam 的限額均可能漏解，沒有窮盡性保證。
- 每次交換記錄進入步、離開步、取色與犧牲色；只允許一次進入後接一次離開，可在轉轉附近反向移動。整條路線的相鄰格、封條、固定起點、色表、交換次序及實際犧牲色都要重播驗證，即使只要求前綴亦檢查後續。珠子身分與附帶欄位跟著交換，轉轉格本身不因重播結束而被改成「成功色」。
- 評估只覆蓋 `releaseColors` 所列的**消除判定時顏色**，不是螢幕看到放手那一刻的顏色。原有全色序評估保持；三消下限、連接群組下限及不可消規則繼續套用。新入口拒絕鎖珠／荊棘／特殊色、多格轉轉、封條上的轉轉及非預設活動評分。
- 搜尋預留同一總額內的 1–25 ms 作重播／最終評估。`planSlicesExpired`、`searchBudgetExhausted`、`deadlineReached` 分別記錄方案額度、搜尋額度與整體時限；珠量尚未檢查完只能回報 `NoRoute`，不能冒充缺珠證明。最後按剩餘時間擴大成功色罩，`evaluatedReleaseColors` 明示實際檢查過的顏色；未檢查的色不當成功。時鐘在有界操作之間檢查，一次排序／評分仍可能略超時，不是硬即時上限。

### 原生時序證據與尚未接入的原因

本輪只讀已保存的 PAD 23.6.1 IDA 資料庫。私有反編譯／指令證據位於忽略目錄 `build/research/fishing-phase-23.6.1/`，不把原版程式或私人紀錄提交到來源。

| PAD 23.6.1 入口 | 靜態觀察 | 對模型的影響 |
|---|---|---|
| `0x1005AB5F4` | 在狀態條件允許時遞減 `impl+0xB4854` 倒數；歸零後只改 `orb+18 == 0` 且未鎖的轉轉珠色 | 等到顏色之前，該格的珠須已停止移動；完整一圈只在更新仍持續時有意義 |
| `0x100608AC0`／`0x100608CF0` | 相鄰／斜向交換會把被換出的珠設成狀態 3，並設定 0.125 的位置插值 | 不能把剛交換的珠立即視為已恢復轉色；0.125 不是已驗證的固定八幀上限 |
| `0x1005B5180` | phase 2 的輸入處理在共同更新器之前 | 同一畫面影格中也可能存在輸入前後的色序差異 |
| `0x10060D578`／`0x100602FA0` | 放手清理與持珠狀態轉換依分支進行，後續轉入等待判定 | 放手不等於立即擷取匹配布局 |
| `0x100603DF4` → `0x1005FC954` | 等狀態 1–3 及部分狀態 4 插值完成，才呼叫匹配 | 從放手到真正匹配之間仍有待確認窗口；轉轉可能在此期間繼續變色 |

現有 [PHOrbNative.mm](../src/PHOrbNative.mm) 只把各珠動作彙成全盤 `settled`，持珠中通常為 false，沒有保留「除目前持珠外皆穩定」供最後色序判斷。本輪沒有新增 reader 欄位、Hook、倒數／珠色寫入或裝置操作。下一次接原生前，仍要核對交換後穩定、讀取與輸入次序、最後放手至匹配的實際幀數與停止行為；靜態入口證據不足以定義可執行窗口。

### 等待時間估算

`PHOrbReserveTimedFishing` 接受明確的每步幀數、每次等待前穩定餘量、輸入／判定餘量、每色週期及剩餘幀數，回傳分項估算。每次取色預留一整圈，若成功色罩不是全部色表，最後再加一圈；每次取色前和最後判定前另計穩定時間。總額必須嚴格小於剩餘時間，未知／零餘量或整數溢位拒絕。

這是呼叫者假設下的算術篩選，不驗證目標達成、不判定實際色序可趕上，也不是裝置執行門檻。原盤每圈 90 幀，兩次取色加最後選色單是等待便預留 270 幀／9 秒；19 秒是否足夠，還要加路線、穩定與輸入／判定餘量，不能僅用九秒宣稱可行。
