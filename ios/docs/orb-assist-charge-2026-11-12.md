# 武裝失效後 Auto 讀取誤停

2026-11-12，來源修正及回歸案例已準備，尚未編譯或執行。原始私人 log 不納入版本；本頁只記必要、去識別的觀察。二進位來源與原生函式證據見 [研究紀錄](../research/orb-assist-charge-20261112.json)。

## Log 能確認的範圍

0.5.45-orbs 在原生 phase 8 留下「技能／敵人資料未通過讀取校驗，已停止」；盤面 `valid=1`、`automationValid=0`，輸入故障數 0。停止點在 `ReadAutomationFields`，尚未走到新的技能決策或補 L 求路。之前的成功／失敗搜尋快照不能代表這次讀取失敗當下的隊員狀態。

舊 log 沒有記錄失敗欄位或 charge／shadow，不能直接證明當次是哪一格不一致。以下是對相符 JP 23.6.1 / 107553 二進位確認的原生行為，以及會導致相同停止的來源缺陷；並非已重播原裝置事故。

## 原生蓄技與副本不一定相等

`member+456` 是技能使用端讀取的受保護蓄技值；`member+1512` 是 XOR `0x68fb65ce` 的帳務副本。既有 Auto 額外要求兩者逐次讀取完全相等。

- `0x10056A118` 在蓄技高於本體 CD 時，只呼叫 `0x10056CBD4(member+456, bodyCD)`。setter 只更新該 protected 欄位及原生亂數狀態，沒有同步寫入副本。
- 敵方武裝失效處理 `0x100566C50` 會在有效武裝描述更新前呼叫此 clamp。`0x1005A1588` 重建隊員時，依失效回合／關卡規則／保留狀態清除有效武裝；有效 ID≤0 時也呼叫同一 clamp。
- 武裝恢復的重建路徑沒有補寫副本。`0x100569F9C` 後续加蓄技時各自增加目前值和副本，並各自飽和於 9999，所以副本仍可能較高。只有部分原生路徑，例如技能重置 `0x1005C5094`、敵方減 CD、重新套用上限，才會同步。

因此，只在 `effectiveAssistID==0` 或武裝失效回合>0 時忽略差異並不足夠：動畫前段及恢復後的下一回合仍可能誤停。也不應呼叫會初始化快取的 CD getter 來修補讀取。

## 修正邊界

單人 Auto reader 保留原本相等的情況；不相等時，只有 `protectedCharge < decodedCopy <= 9999` 才接受。由四個 word 解出的三份 protected 值仍須一致，無法讀取、較低副本、超範圍副本仍拒絕。快照只儲存真正的 protected charge，副本不參與技能 CD 或本體／武裝選擇，也沒有寫回任一原生數值。

這是合法 native clamp 的單向範圍檢查，不能單憑較高副本證明曾發生武裝失效。實際施放仍使用原生 can-use、指定技能來源、操作窗口及前後快照核對；較高副本不能提供額外蓄技權限。8P 固定隊伍讀取與入場／換隊的 charge 檢查保持完全相等。

失敗訊息改為具體資料類別，隊員欄位包含位置；蓄技副本不一致時記錄實際讀到的目前值／副本。這些訊息沿用 `lastReadIssue.reason` 保存，不新增指標、帳號資料或常駐歷史。每次刷新先清除 `automation.valid`，避免失敗後殘留上一份有效標記。

## 已寫、待執行的驗證

- 原生記憶體案例：20→5 clamp、phase 8／2、有效武裝描述重建前後；唯讀且不呼叫 getters；新鮮補 L 雙讀仍能取得目前本體 L 與保留武裝。
- 技能案例：失效／恢復後的本體施放，較高副本不能選武裝，真實冷卻不足／原生拒絕仍拒絕，can-use 期間蓄技變化仍撤銷。
- 損壞案例：副本低於目前值、超過 9999、protected 成分損壞、舊有效快照刷新失敗；確認錯誤包含位置與欄位。
- 8P 案例：較高副本仍失敗；沒有扩大多人 Auto 或技能授權。
- Session 案例：phase 8 等待、穩定後補 L、武裝恢復後下一回合繼續。此替身流程沒有執行原生 clamp 或模擬遊戲實際 L 結算；原生位元組案例另行覆蓋。

本批只做來源審查、格式與差異檢查；macOS native／Session、完整回歸、iPhoneOS 編譯與真機失效／恢復循環仍待「編譯測試」。0.5.45 及更早的測試結果不作為本批驗證。
