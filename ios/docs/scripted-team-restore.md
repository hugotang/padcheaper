# 有腳本關卡的套隊與整隊還原

0.5.5-orbs；日服 iOS 23.6.0／106878。只支援單人。

使用者提供的 0.5.4 log 表明位置 1–5 曾還原但校驗失敗後回復，位置 6 成功；並非剩餘排程遺失。原生武裝描述的 byte 7 是填充，無武裝時 bytes 4–5 也未初始化，逐 byte 比較可能誤判失敗。新版正規化這些無意義欄位，仍嚴格核對其餘培養及武裝。舊 log 沒有細分欄位，尚不能斷定這是該次失敗的唯一原因。

失敗會保留每個位置的原因及「重試未完成還原」入口，最後成功一格不會蓋掉失敗摘要。重試成功才釋放剩餘記錄，然後可套用另一隊；不得僅清除記錄後強套。若原生回復無法確認，原場繼續停止寫入；確認離場／不同戰鬥後不延續舊故障。新增 native／session 的六格還原、五格失敗後重試及另一隊套用案例，驗證結果見 [開發記錄](development.md)。

## 使用者回報與可確定的原因

使用者的 3600 秒關卡診斷顯示 `phase 2 / flags 0x45 / mode 1 / source 0 / multi 0`，手動與自動套用均回報「此關卡的編隊腳本正在使用參數」。`Current entry: applied 0` 表示本次入場未成功；`count 4 / last SB 19` 是先前累計結果。六名隊員 `script -1 / provider 0` 不代表全域腳本沒有事件。

0.5.3 的 `ReadIdleContext` 要求全部 157 個事件入口都是 UINT32_MAX。演出、BGM 和文字事件也會被當成編隊參數占用，因此檢查確實比參數衝突條件更嚴。舊訊息還把 runner 正在執行、記憶體讀取失敗、十個槽均占用等原因合併；僅憑舊 log 不能確定這次是哪一項。背景計時旗標不參與這個檢查。

使用者另回報「還原隊伍有時只還原一隻」。舊 provider 在 runner 非零或 context 暫時無法讀取時不附加 ownership token；session 隨即把仍有原生來源的隊員當成遊戲接管，清掉剩餘還原紀錄。這是可由程式與回歸案例重現的缺陷；尚無該次裝置還原當下的診斷，不能宣稱已證實為唯一原因。

## 新的相容條件

- 檢查初始 bytecode 入口及全部已註冊事件。文字指令用原生長度跳過，其餘指令按換行結束；拒絕越界、未知 opcode、未終止內容及落在指令內部的事件入口。
- 保留遊戲配置的原始 program、pool 和事件表。只有全部入口不含 opcode 26（`#party`）的腳本，才可借用十個 44-byte 記錄中的全零且未引用空槽。
- `#party param` 可能稍後才取得當下為空的槽，`#party set` 可改變隊伍來源。因此含任一 `#party` 指令的關卡仍不套完整隊伍；不以「目前空槽」推定往後安全。
- 腳本長度從原生 allocator 標頭取得：回傳指標前 56 bytes、標頭 +4 為大小、+8 為 category/tag 4/44。大小需符合編譯器的 `float(sourceLength) * 1.5` 且不超過 1 MiB；不掃描未證實屬於該配置的頁面。
- 借用期間逐次核對原始 bytecode、事件入口、program／pool／來源長度及記錄內容。事件執行次數不作為 ownership 身分；任何寫入仍要求 runner 空閒。

完整自動套隊維持只在新入場 wave 0 動畫處理一次，手動套用維持操作階段及原有充能。帶編隊指令、腳本載入中或 runner 尚未停止的關卡有明確訊息，不保證所有計時關卡可套用。

## 還原排程

讀取 ownership 和允許寫入分開：演出中的有效來源可維持 token，但先等待再還原。context／record 暫時讀不到時標為「未能確認」，保留原配方與排程；可讀且已改變的記錄才視為真正接管。未知來源不執行寫入。

按還原會停止自動轉珠／技能排程，已啟動的原生技能仍由遊戲完成。還原或套隊進行中不能重新開始轉珠。每成功一格顯示剩餘數量；失敗顯示具體位置，診斷保留 pending／failed／provider uncertain masks。已確定回復的單格失敗不會無限重試，其他待還原位置可繼續；不確定回復仍停止全部原生寫入。

複製診斷新增 `Battle script:`（可讀、program、runner、事件數、來源長度、空槽 mask）及 `Battle restore:`。若新版仍只能還原一隻，這兩行與 `Battle:` 可區分等待動畫、來源確認及單格失敗。

## 原生依據與測試

IDA 核對原始 executable SHA-256 `611c93f5472fceddfa27254b718c6eff1decdc6814cc927e2faa4c7c250a65ec`：compiler `0x100595098`、dispatcher `0x10059B34C`（opcode 檢查 `0x10059B5A4`）、party `0x10059A848`、allocator `0x10058E5AC`、member rebuild `0x1005A12F0`。新增四組 64-byte 指紋，不呼叫 compiler 或中間指令。

模型案例涵蓋最後一個事件、重複／未排序入口、文字 payload、延後編隊指令及越界。原生案例涵蓋 mode 1 手動／新入場六格、原腳本保存、還原一格後 runner 啟動、讀取失敗恢復、bytecode 改變、真實接管與零寫入拒絕；session 案例涵蓋還原一格後暫停再自動完成其餘五格。實際執行結果見 [開發紀錄](development.md)，案例存在不代表真機通過。
